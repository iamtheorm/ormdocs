The Cloud Infrastructure Runbook (AWS)

Highly Available IoT Energy Optimization Platform

01 / Overview

Introduction to the Operational Blueprint

Operating a highly available, scalable internet of things (IoT) energy optimization platform on Amazon Web Services (AWS) requires strict adherence to the AWS Well-Architected Framework. The deployment of an enterprise-grade IoT platform—responsible for ingesting millions of telemetry records from distributed energy assets, processing them in real-time, and executing automated control algorithms—demands an architecture that prioritizes fault isolation, data durability, and zero-downtime continuous integration and continuous deployment (CI/CD).

This operations manual serves as the definitive runbook for Site Reliability Engineering (SRE) and DevOps teams. A standard runbook must provide actionable, step-by-step operational guidance for handling recurring tasks, alert remediation, and deployment procedures, ensuring that engineers have the necessary context to prevent destructive actions without being overwhelmed by extraneous theory. To satisfy these requirements, this document exhaustively details the reference architecture, network topology, minimum-privilege security guardrails, edge-device resilience strategies, database migration methodologies, and explicit deployment rollback procedures.

By utilizing infrastructure as code (IaC) and serverless components, the architecture inherently aligns with the Reliability and Operational Excellence pillars of the Well-Architected Framework, effectively reducing toil and standardizing failure management across the fleet.

02 / Topology

Reference Architecture and Network Topology

The foundation of a resilient cloud environment is a rigorously partitioned Virtual Private Cloud (VPC) topology that enforces cross-Availability Zone (AZ) high availability and strict ingress/egress controls. The platform utilizes a multi-AZ deployment strategy across a minimum of three isolated Availability Zones to guarantee fault tolerance and 99.999999999% durability for object storage systems.

The Three-Tier VPC Architecture

The network is logically segmented into three distinct subnet tiers, each serving a specific security boundary and workload function:

  • Public Ingress Tier: This tier hosts the Application Load Balancers (ALB) and NAT Gateways. It is the only subnet equipped with a default route to an Internet Gateway (IGW). External traffic from web dashboards and operator APIs enters exclusively through the ALBs, which terminate TLS connections and forward traffic to the internal compute tier.
  • Private Compute Tier: This tier hosts the Amazon Elastic Container Service (ECS) Fargate tasks, internal microservices, and AWS Lambda functions responsible for telemetry enrichment. Resources in this tier have no direct internet access; outbound requests (e.g., reaching third-party weather APIs for energy forecasting) are routed strictly through the NAT Gateways residing in the public tier.
  • Isolated Data Tier: The lowest level of the network topology contains the persistent datastores, primarily Amazon Aurora Serverless v2 clusters and Amazon ElastiCache instances. This tier is intentionally designed without any outbound route to the internet, providing a logical air-gap that prevents data exfiltration even if the compute tier is compromised.

The integration between the edge devices, the serverless ingestion pipeline, and the synchronous application programming interfaces (APIs) forms a continuous, event-driven ecosystem.

03 / Ingestion

IoT Telemetry Ingestion and Edge Connectivity

Ingesting millions of small payload records (typically under 4 KB) per minute requires a pipeline capable of absorbing severe backpressure and sudden traffic spikes. The architecture segregates command-and-control operations from read-only telemetry by enforcing strict MQTT topic namespaces. Telemetry data is published to prefixes such as data/device/sensortype, while control plane operations use the command/ prefix.

Managing Kinesis Data Firehose Backpressure

The AWS IoT Rules Engine continuously intercepts MQTT messages and routes them to Amazon Kinesis Data Firehose for batching and delivery to an Amazon S3 data lake. Because energy optimization models require rich context, a data transformation AWS Lambda function is configured within the Firehose delivery stream to enrich incoming payloads (e.g., attaching facility geolocation or hardware metadata retrieved from DynamoDB).

Operational disruptions frequently manifest as throttling within this pipeline. If the data source involves a standard Kinesis Data Stream upstream of Firehose, the pipeline is bound by a hard limit of five transactions per second (TPS) on the GetRecords API. Exceeding this limit yields ThrottledGetRecords exceptions, which can result in data loss if the retention window is exceeded.

To mitigate delivery failures, operators must implement the following safeguards:

  • Buffering Hints: Configure Firehose buffering hints to maximums (e.g., 5 MB or 60 seconds) to reduce the frequency of downstream API calls and optimize the batch sizes written to Amazon S3.
  • Transformation State Contracts: The inline Lambda function must strictly adhere to the Firehose response contract, returning a status of Ok for successfully enriched records, Dropped for payloads that fail schema validation, or ProcessingFailed for transient backend errors.
  • Compute Scaling: If Firehose delivery falls behind ingestion rates, the root cause is frequently a slow Lambda invocation executing network I/O. The runbook requires increasing the Lambda function's memory allocation, which proportionally increases the allocated CPU threads, allowing the asynchronous I/O operations to process faster.

Mitigating Connection Storms and Thundering Herds

A highly documented failure mode in large-scale IoT fleets is the "thundering herd" problem. When a regional internet service provider experiences an outage, millions of smart energy meters may disconnect simultaneously. Upon network restoration, these devices will attempt to reconnect to AWS IoT Core concurrently.

If devices immediately retry failed connections, the synchronized traffic spike acts as a self-inflicted Distributed Denial of Service (DDoS) attack against the cloud infrastructure, overwhelming the IoT Core message broker and custom authorization Lambdas. Furthermore, standard exponential backoff (e.g., waiting 100ms, then 200ms, then 400ms) spaces the traffic out but fails to alter the shape of the spike, creating a series of delayed, synchronized waves.

To achieve true system resilience, remote devices connecting to the cloud must implement exponential backoff combined with jitter. Jitter introduces randomness to the retry delay, explicitly desynchronizing the fleet.

Jitter Algorithm Logic System Impact
Full Jitter Random value between 0 and the current exponential maximum: random(0, min(cap, base * 2^attempt)) Yields the lowest overall workload contention and is the safest approach for large-scale fleets.
Equal Jitter Holds half the wait fixed and randomizes the remaining half. Prevents extremely short sleeps but performs slightly worse than Full Jitter regarding total system load.
Decorrelated Jitter Ignores the attempt counter, growing the delay based on the previous random sleep value. Reaches the maximum delay cap faster, which can delay recovery times for fast-resolving outages.

The runbook mandates the deployment of the Full Jitter algorithm across all C-based FreeRTOS edge devices and Python SDKs. Below is the required Python implementation for AWS IoT edge SDKs enforcing exponential backoff with Full Jitter:

import time
import random
from functools import wraps
from botocore.exceptions import ClientError

def retry_with_full_jitter(max_retries=5, base_delay=1, max_delay=60):
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            retries = 0
            while retries < max_retries:
                try:
                    # Attempt the network operation
                    return func(*args, **kwargs)
                except ClientError as e:
                    error_code = e.response['Error']['Code']
                    
                    # Fail fast for deterministic client errors
                    if error_code in ['AccessDeniedException', 'ValidationException']:
                        raise e
                    
                    # Apply Full Jitter: random(0, min(cap, base * 2^attempt))
                    exponential_window = min(max_delay, base * (2 ** retries))
                    sleep_time = random.uniform(0, exponential_window)
                    
                    time.sleep(sleep_time)
                    retries += 1
                    
            raise Exception("Maximum retries exhausted due to persistent network failures.")
        return wrapper
    return decorator

04 / Security

Identity and Access Management (IAM): Minimum Privilege Guardrails

Ensuring a highly secure environment requires layering network perimeter controls with strict, identity-based permissions boundaries. The operations team is responsible for ensuring that any access granted—whether to human operators or machine identities—adheres strictly to the principle of least privilege.

VPC Endpoint Policies

To protect sensitive operational data, the platform utilizes AWS PrivateLink (VPC Endpoints) to interact with AWS managed services such as Amazon S3, AWS Key Management Service (KMS), and Amazon Timestream. This ensures that traffic never traverses the public internet.

To enforce this architecture programmatically, S3 bucket policies and KMS key policies utilize the aws:SourceVpc condition key. This IAM condition enforces that any successful API call must originate from the specified VPC. Relying on the aws:SourceVpc key is a proven best practice over the aws:SourceVpce (VPC Endpoint ID) key, as endpoint IDs are ephemeral and can change if the infrastructure is redeployed via Terraform or AWS CloudFormation, whereas the VPC ID remains a static identifier.

An example of a highly restrictive, minimum-privilege S3 bucket policy for the telemetry data lake is provided below:

X.509 Certificate Management and Automated Rotation

AWS IoT Core enforces Transport Layer Security (TLS 1.3) mutual authentication using X.509 certificates to establish a trusted connection between the edge devices and the cloud broker. These certificates are the core of device identity and are inherently long-lived; however, organizational security policies require scheduled rotation of the certificate and private key to minimize exposure if hardware is physically compromised.

The runbook dictates an automated, over-the-air (OTA) certificate rotation workflow utilizing AWS IoT Device Defender. The platform schedules continuous audit checks, explicitly leveraging DEVICE_CERTIFICATE_EXPIRING_CHECK to identify credentials within 30 days of expiration, and DEVICE_CERTIFICATE_AGE_CHECK to flag certificates exceeding a strict organizational age limit (e.g., 12 months).

IoT Device Defender Anomalous Behavior Detection

Beyond static certificate audits, the platform employs AWS IoT Device Defender's Machine Learning (ML) and rules-based detect features to monitor for active intrusions.

Metric Target IoT Defender Variable Operational Implication
Payload Volume aws:message-byte-size Sudden spikes in byte size frequently indicate a compromised device attempting to exfiltrate lateral data or inject malicious shellcode.
Authentication Integrity aws:num-authorization-failures High concentrations of failures imply that a certificate has been revoked, or an attacker is attempting a brute-force connection utilizing malformed credentials.
Connection Stability aws:num-disconnects Rapid disconnect/reconnect loops often point to underlying hardware degradation, power source failure, or a synchronized thundering herd scenario.

Application Deployment and Container Orchestration

The core API layers of the energy optimization platform are executed as stateless, containerized applications managed by Amazon Elastic Container Service (ECS) utilizing the AWS Fargate serverless compute engine. Fargate abstracts away the underlying EC2 instances, offloading operating system patching and host security to AWS.

OpenTelemetry Sidecar Configuration

Comprehensive observability is non-negotiable for SRE teams tasked with monitoring a distributed microservice architecture. To facilitate distributed tracing and high-resolution metric collection, an AWS Distro for OpenTelemetry (ADOT) sidecar container must be deployed within every ECS Task Definition.

ECS Rolling Update Mathematics

When updating the container images or configuration, ECS relies on the ECS rolling update deployment type. The safety, speed, and capacity impact of a rolling deployment are dictated entirely by two mathematical parameters: minimumHealthyPercent and maximumPercent.

Deployment Scenario minimumHealthyPercent maximumPercent Operational Impact
Mission-Critical (Zero-Capacity Drop) 100% 200% Ensures the platform never dips below optimal capacity. The scheduler starts replacement tasks up to double the desired count before terminating any older tasks.
Resource-Constrained Cluster 50% 100% Forces ECS to terminate older tasks to make room for newer ones. Operates at a maximum of the desired count, meaning the application will experience a temporary 50% capacity reduction.
Cost-Sensitive Hybrid 50% 150% Provides a balanced approach, allowing ECS to fluctuate slightly above and below the baseline capacity, mitigating severe outages while saving on compute overhead.

Automated Rollback Procedures and Circuit Breakers

In modern cloud architecture, human intervention during a failed deployment is an anti-pattern. Manual remediation increases Mean Time to Recovery (MTTR) and introduces catastrophic human error. The runbook requires that all deployments utilize automated circuit breakers to detect failures and revert state instantly.

To solve this, ECS natively integrates with Amazon CloudWatch alarms. The operations team provisions an alarm monitoring the Application Load Balancer's TargetResponseTime and HTTPCode_Target_5XX_Count metrics. If the response time breaches an acceptable baseline at any point during the deployment rollout window, the alarm transitions from OK to ALARM.

The AWS CLI command used by the CI/CD pipeline to initiate this highly resilient deployment mechanism is explicitly detailed below:

aws ecs update-service \
  --cluster energy-platform-cluster \
  --service telemetry-ingestion-api \
  --task-definition energy-api:v2 \
  --deployment-configuration "maximumPercent=200,minimumHealthyPercent=100,deploymentCircuitBreaker={enable=true,rollback=true},alarms={alarmNames=[HighResponseLatencyAlarm, API5xxErrorAlarm],enable=true,rollback=true}"

Zero-Downtime Database Schema Migrations

Modifying relational database schemas in production is historically the highest-risk operation in software engineering. A poorly executed migration can lock tables entirely, backing up incoming API requests, exhausting database connection pools, and effectively halting the energy optimization platform.

Feature Flyway Liquibase
Migration Format Raw SQL files (V1__Add_Column.sql) or Java code. SQL, XML, YAML, JSON abstractions.
Rollback Strategy Requires manually written undo scripts; automatic rollbacks are gated behind commercial tiers. Offers auto-generated rollbacks for many built-in structural change types on the free tier.
State Tracking Ledger Uses the flyway_schema_history table. Uses the databasechangelog table.
Ideal Operational Fit Teams managing a single database engine that prioritize raw SQL visibility and simplicity. Teams requiring database-agnostic code across multiple environments.

The Expand-Contract (Parallel Change) Pattern

To achieve true zero-downtime database changes, all migrations must adhere to the Expand-Contract pattern. This methodology breaks down potentially destructive schema changes (such as renaming or splitting a column) into non-breaking, multi-phase deployments, explicitly preventing the need for heavy exclusive table locks that block PostgreSQL read/write operations.

Phase 1: Expand (Additive Schema Change)

ALTER TABLE devices ADD COLUMN city VARCHAR(100);
ALTER TABLE devices ADD COLUMN zip_code VARCHAR(20);

Phase 2: Migrate (Asynchronous Data Backfill)

UPDATE devices 
SET city = split_part(device_address, ',', 1), 
    zip_code = split_part(device_address, ',', 2) 
WHERE city IS NULL;

Phase 3: Contract (Cleanup and Deprecation)

ALTER TABLE devices DROP COLUMN device_address;

A critical operational note: when deploying new indexes to the production PostgreSQL tables, the CONCURRENTLY keyword is absolutely mandatory. Executing a standard CREATE INDEX without this keyword immediately places an exclusive lock on the table, blocking all incoming INSERT and UPDATE statements from the IoT telemetry pipeline until the index finishes building.

07 / Recovery

Disaster Recovery and Data Resilience

Disaster Recovery (DR) in the AWS Cloud is quantified through two overarching business metrics: the Recovery Time Objective (RTO) and the Recovery Point Objective (RPO).

  • Recovery Time Objective (RTO): Denotes the maximum tolerable duration the application can remain offline following a catastrophic event. It defines the speed of the recovery process.
  • Recovery Point Objective (RPO): Denotes the maximum acceptable loss of data, measured backward in time from the point of failure. It defines the necessary frequency of database backups and replication.

To support mission-critical energy optimization grids, the RPO target is strictly defined as under 5 minutes, and the RTO is set at a maximum of 15 minutes. To achieve this level of resilience, the platform leverages Amazon Aurora Serverless v2 configured as an Aurora Global Database.

In the event of a total regional outage in the primary deployment (e.g., us-east-1), the runbook dictates promoting the secondary read replica (e.g., us-west-2) to act as the primary cluster. Because Aurora Serverless v2 decouples compute from storage, the secondary region can scale its compute heads instantly to absorb the rerouted traffic, meeting the strict 15-minute RTO. Concurrently, Amazon Route 53 health checks detect the regional failure and seamlessly redirect incoming API and IoT MQTT traffic to the surviving infrastructure.

By enforcing rigorous CI/CD practices, robust telemetry pipelines, minimum-privilege IAM controls, and fully automated deployment rollbacks, this operations runbook ensures that the AWS infrastructure remains exceptionally resilient against both external malicious vectors and internal operational errors.
